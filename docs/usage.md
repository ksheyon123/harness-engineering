# 사용법 — 사람은 언제 무엇을 하나

**설치가 끝난 뒤 여는 문서다.** 설치는 [`implementation.md`](./implementation.md) 가 덮는다.

여기는 절차서가 아니다. 절차는 `.claude/harness.md` 에 있고 **그건 에이전트가 읽는다.** 이 문서가 답하는 것은 하나다 — **너에게 무엇이 보이고, 언제 네 차례인가.**

> **지금은 Windows 에서만 돈다.** 작업 세션을 띄우는 `harness spawn` 이 PowerShell 이라, 그 밖에서는 파이프라인 전체를 못 쓴다. 직접 `claude` 를 열어 역할을 말로 심는 것은 대안이 **아니다** — 아래 [못 하는 것](#못-하는-것--전부-의도다) 마지막 행에 이유가 있다.

## 한 요청이 끝까지 가는 모습

**탭이 둘이다.** 하나는 항상 떠 있고(맨몸 `claude`), 하나는 task 마다 새로 열렸다 닫힌다.

```
탭 1 — 맨몸 claude               탭 2 — 작업 세션 (spawn 이 띄운다)
  │
  │ "로그인 만들어줘"        ①
  ├────────────────────────────▶ 탭이 열리면서 논의가 시작된다
  │                                │
  │                                │  ❓ Q1 … ➡️ 추천안        ②
  │                                │  (답하면 다음 라운드)
  │                                │
  │                                │  spec.md 를 보여준다      ③
  │                                │  ─── 승인 = spec 커밋 ───
  │                                │
  │                                │  여기서부터 안 묻는다
  │                                │  개발자 → 머지 → 게이트
  │                                │  QA → 최종 게이트 → push
  │                                │
  │                                ▼  보고. 탭을 닫는다
  │
  ▼ PR 을 본다                 ④
```

**네 번뿐이다.** ③ 에서 승인하고 나면 자리를 떠도 된다 — 그 뒤로는 물어보지 않는다(예외는 [멈춤 조건](#막혔을-때) 뿐이다).

## 네 번의 차례

### ① 요청한다 — 맨몸 탭에서, **원문 그대로**

**요약하지 마라.** 실행자는 네가 친 원문을 그대로 작업 세션에 싣는다. 요약해서 주면 spec 이 그 요약 수준에서 멈춘다 — 재료가 그것뿐이기 때문이다.

무엇이 어디로 가는지는 실행자가 판정한다:

| 네가 말한 것 | 어디서 처리되나 |
|---|---|
| "로그인 만들어줘" · "이 오타 고쳐줘" · "리팩터해줘" | **탭이 하나 열린다** — 결국 코드가 남는다 |
| "로그인 어떻게 만들까" | **탭이 하나 열린다** — 아직 코드는 안 바뀌어도 결국 남는다 |
| "이 함수 뭐 하는 거야" · "이거 왜 실패해?" · "PR 좀 봐줘" | 그 자리에서 답한다 |
| "훅을 이렇게 바꾸면 어떨까" · 설정·규약 문서 수정 | 그 자리에서 한다 — 하네스는 실행자의 본업이다 |

**`/task` 를 칠 필요는 없다.** 그건 판정을 건너뛰는 지름길이지 조건이 아니다. 맨몸으로 말해도 그대로 처리된다.

### ② 질문에 답한다 — 여기가 유일하게 대화가 본업인 구간이다

새 탭이 열리면 곧바로 질문이 온다. 형식은 이렇다:

```
❓ **Q1** - **<제목>**: <본문 · 선택지>

➡️ <추천안>
```

- **라운드로 온다.** 지금 답할 수 있는 질문만 한 묶음으로 오고, 네 답이 다음 묶음을 연다.
- **추천안이 붙는다.** 동의하면 `1, 2 동의. 3 은 B 로.` 한 줄이면 된다.
- **사실은 안 묻는다.** 파일이 어디 있는지, 기존 구현이 어떤지는 세션이 직접 찾는다. 너에게 오는 것은 **결정**뿐이다.
- 질문이 다 떨어지면 spec 을 쓴다. 그게 ③ 이다.

논의 방식 자체를 바꾸고 싶으면 [팀에 맞추기](#팀에-맞추기) 를 봐라 — `.claude/planner/` 를 갈아끼우면 된다.

### ③ spec 을 승인한다 — **이것이 유일한 실질 통제점이다**

승인하면 그 spec 이 커밋되고, **그 뒤로는 아무도 그 파일을 고치지 않는다.** 저자인 세션도 마찬가지다. 그러니 여기서 봐야 한다:

| 절 | 무엇을 확인하나 | 놓치면 |
|---|---|---|
| `## 인수기준` | **검증 가능한 단언인가.** 값으로 쓸 수 있는 것이 값으로 쓰였나 (`[(0,0),(1,1)] → [(0,0)]`) | "로그인이 잘 동작한다" 같은 문장은 테스트로 못 옮긴다. 해피패스만 덮어도 green 이고 QA 도 대조할 기준이 없다 |
| `## 범위 밖` | 내가 생각한 경계와 같나 | 개발자는 자율 진행이라 **선의로 범위를 넓힌다.** 그걸 막는 유일한 문장이 여기다 |
| `## 버린 대안` | 내가 기각한 접근이 **이유와 함께** 적혔나 | 이유 없이 "안 쓴다"만 있으면 개발자가 "더 짧은데요" 하고 갈아탄다 |
| `## 배경` | 몇 달 뒤 이 파일만 읽고 왜인지 복원되나 | PR 을 보는 사람에게 남는 근거가 없다 |

**기준은 하나로 줄일 수 있다 — "이 파일만 읽고 구현할 수 있나."** 개발자도 QA도 PR 을 보는 사람도 이 파일만 본다. 대화는 탭이 닫히면 사라진다.

고칠 것이 있으면 **승인 전에** 말하면 된다. 아직 1모드라 얼마든지 고쳐 쓴다. 승인 뒤에 발견하면 [리비전](#막혔을-때)이고, 새 브랜치가 필요하다.

### ④ PR 을 본다 — 최종 확인자는 사람이다

브랜치에 셋이 올라온다:

| 무엇 | 누가 썼나 |
|---|---|
| `harness/<task>/spec.md` | ③ 에서 네가 승인한 것 |
| `harness/<task>/qa-checklist.md` | QA — 인수기준 대 테스트 대조표 |
| 코드 + 테스트 | 개발자 |

**읽는 순서가 있다: 인수기준 → 체크리스트의 그 행 → (필요하면) 코드.**

체크리스트는 인수기준 한 줄마다 한 행이고, 판정이 넷이다:

| 판정 | 뜻 | 네가 할 판단 |
|:---:|---|---|
| ✅ | 온전히 검증하는 테스트가 있다 (근거로 테스트 이름이 인용돼 있다) | — |
| △ | 일부만 덮는다 | 엣지 케이스를 더 시킬지 |
| ❌ *(구현 있음)* | 겨냥한 테스트가 없다 | 테스트를 더 시킬지 |
| ❌ *(구현 없음)* | 테스트도 구현도 없다 | **spec 미이행이거나 spec 이 틀렸다** |

두 가지를 알고 봐라:

- **게이트가 green 이라는 건 "테스트가 통과했다"이지 "테스트가 spec 을 덮는다"가 아니다.** 뒤엣것에 답하는 것이 이 표다. 게이트는 구조적으로 그걸 볼 수 없다.
- **QA 는 아무것도 막지 않는다.** `❌` 가 있어도 push 된다. 설계가 그렇다 — 판단은 사람 몫이고, 막게 하면 QA 가 게이트를 흉내내다 둘 다 못한다.

**머지는 사람이 한다.** 하네스는 push 까지만 하고 손을 뗀다.

## 못 하는 것 — 전부 의도다

벽처럼 보이는 것들인데, 하나하나 이유가 있다.

| 하려던 것 | 어떻게 되나 | 왜 | 대신 |
|---|---|---|---|
| 맨몸 탭에서 "이 코드 고쳐줘" | 편집이 거부된다 | 허용하면 **spec 없이 동작이 바뀌고 아무도 모른다.** 오타 하나도 예외가 아니다 — 예외를 두는 순간 "인수기준이 바뀌나?"를 실행자가 판정하게 된다 | 그냥 말해라. 실행자가 탭을 띄운다 |
| 작업 세션 탭에 **두 번째** task 를 준다 | 안 받는다 | 이전 논의를 기억한 채로 다음 spec 을 쓰게 되고, 얇게 쓴 뒤 나머지를 프롬프트로 메울 수 있다. **이 하네스가 막으려는 실패 그 자체다** | 탭을 닫고 맨몸 탭에서 새로 요청 |
| 승인된 spec 을 고친다 | 세션이 거부하고 멈춘다 | 고칠 수 있으면 승인이 승인이 아니다 | 새 브랜치에서 리비전 (아래) |
| 2모드에서 "이건 어떻게 할까?" 를 기대한다 | 안 묻는다 | 물으면 자동화가 아니다. 인수기준에 영향 없는 선택은 택하고 **사후 보고에 한 줄로 남긴다** | 정하고 싶은 것은 ③ 전에 말한다 |
| `main` 에 push / force-push | 안 한다 | 비가역이라 사람에게 위임한다 | 직접 한다 |
| 맨몸 `claude` 를 열고 "너는 작업 세션이야" | **안 통한다** | 역할 판정 근거가 대화가 아니라 프로세스 환경(`HARNESS_ROLE`)이다. 세션은 그걸 만들어낼 수 없고, 말로 덮은 역할은 `/clear` 한 번에 사라진다 | `harness spawn` 으로 연다 |

## 막혔을 때

**설치 문제는 여기 없다** — [`implementation.md` 의 막히는 자리](./implementation.md#막히는-자리) 로 가라. 여기는 돌리는 중에 생기는 것만이다.

| 증상 | 무슨 일이 일어난 것 | 네가 할 것 |
|---|---|---|
| 2모드인데 세션이 물어왔다 | **멈춤 조건**이다 — 닫힌 집합이고 넷뿐이다(범위 밖 · 비가역 행위 · 인수기준 모호 · 외부 원인 실패). 커밋도 안 하고 서 있다 | 답하면 이어간다. **"인수기준이 모호하다"면 spec 을 고쳐서 풀지 않는다** — 리비전이 필요하다는 뜻이다 |
| spec 이 틀린 걸 뒤늦게 알았다 | 그 브랜치는 spec 을 이미 한 번 확정했다. `pre-commit` 이 한 브랜치에 spec 둘을 거부한다 | 원본에서 **새 task 브랜치**를 자르고 거기서 기획자 모드로 다시 시작한다. 기존 spec 의 해당 기능만 고치고 `## 개정 이력` 에 한 줄 남는다 |
| "developer 가 red 로 끝났다" 는 신호가 떴다 | 종료 게이트의 재시도 상한(3회)이 소진됐다. 커밋은 되어 있다 | 세션이 머지 전에 확인한다. 보고를 보고 판단해라 — 게이트 자체가 없거나 안 도는 경우가 흔하다 |
| 통합 게이트가 red 다 | 각자의 사본에서는 green 인데 합치니 깨진 것 | **사람이 할 일은 없다.** 세션이 머지된 `HEAD` 에서 개발자를 새로 스폰해 복구한다 |
| 회수할 커밋이 없는데 아무 신호도 없다 | 서브에이전트가 **승인 프롬프트에서 멈춘 것**이다. 멈춤은 종료가 아니라 종료 훅이 안 돌고, 게이트도 인계 커밋도 없다 | 세션에 다시 스폰시킨다. 반복되면 하네스 문제다 — 맨몸 탭에서 말해라 |
| 세션이 죽어 `.claude/worktrees/` 에 사본이 남았다 | `harness reap` 은 한 task 의 push 직후에만 돌고, **자기 task 에 회수된 것만** 거둔다. 남의 것을 지우면 돌고 있는 작업이 깨진다 | 디스크만 먹는다. `git worktree list` 로 보고 사람이 지운다 |
| PR 브랜치 이름이 `worktree-feat+login` 이다 | `EnterWorktree` 가 이름을 그렇게 바꾼다. 격리에 들어가자마자 세션이 `git branch -m` 으로 고쳤어야 한다 | push 전이면 고치라고 하면 된다. **push 후에는 원격 브랜치 삭제까지 얽힌다** |

## 매일 쓰는 명령

| 명령 | 언제 |
|---|---|
| `harness spawn "<원문>"` | 기능 요청이 왔을 때. 작업 세션을 새 탭에 띄운다 (**Windows 전용**) |
| `harness reap` | 한 task 의 push 직후, `ExitWorktree` **전에**. 회수가 끝난 사본을 거둔다 |
| `harness gate` | 게이트를 돌릴 때. **`npm test` 를 손으로 치지 마라** — 검사는 되지만 통과 기록이 안 남아 push 에서 막힌다 |
| `harness doctor` | 설정(`harness.config.json`)의 **값**이 의심될 때 |
| `harness smoke` | **배선**이 끊겼는지 의심될 때 — 훅이 실재하는 파일을 가리키는지 · 돌아 판정을 내놓는지 · 전부 커밋됐는지 |
| `harness sync` | 패키지를 올린 뒤. 저장소에 복사된 규약·에이전트 정의를 다시 쓴다 |

**앞의 셋은 세션이 부른다.** 사람이 직접 칠 일은 드물다 — 뒤의 셋이 사람의 명령이다.

## 팀에 맞추기

| 어디 | 무엇을 바꾸나 |
|---|---|
| `.claude/planner/*.md` | **논의 방식**(② 의 질문 형식). 기본은 `grilling.md` 다. **디렉터리가 곧 스위치다** — 지우면 안 묻고, 바꾸면 그대로 돌고, 더하면 다 실린다. 작업 세션에만 붙는다 |
| `.claude/rules/*.md` | 경로별 코딩 규약. `paths:` frontmatter 를 붙이면 **매칭되는 파일을 읽을 때만** 로드된다 — 빼면 매 세션 실려 분리한 의미가 없어진다 |
| `.claude/harness.config.json` | 게이트 명령 · 소스 경로 · spec 위치 · 보호 브랜치. 값과 기본값은 [`implementation.md`](./implementation.md#프로젝트에-맞추기--harnessconfigjson) 에 있다 |
| `.claude/agents/developer.md` | 개발자에게 주는 지시(테스트 스타일 등). **`harness sync` 가 덮어쓰려 하면 알리고 멈춘다** — 손댄 파일은 덮지 않는다 |
