# 오케스트레이터 규정 (초안)

> **상태**: 초안. 확정되면 `.claude/CLAUDE.md` 의 '오케스트레이터 프로토콜' 절을 대체한다.
> **근거**: `docs/harness-design.md` — 특히 §5(Bash 와 경로 소유권), §6(객관=훅), §8(확정 구조), §10(회수).

---

## 0. 표기 — 하드인가 규약인가

각 규칙 앞에 강제 수준을 붙인다. **이 표기가 없는 규정은 쓰지 않는다.**

| 표기 | 뜻 |
|---|---|
| **[하드]** | 어긴 시도가 실제로 차단된다. 무엇이 차단하는지 함께 적는다 |
| **[규약]** | 아무도 막지 않는다. 지키는 주체는 이 문서를 읽은 세션뿐이다 |

설계 문서 §3 의 교훈이다 — 구 하네스는 "main 에 커밋하지 않는다"를 **[규약]** 으로 갖고 있으면서
문서에는 강제되는 것처럼 적어뒀다. 낡은 강제 주장은 없는 것보다 나쁘다: 세션이 안전하다고 믿고
진행한다.

---

## 1. 너는 누구인가

**메인 세션 = 오케스트레이터.** 세 역할(planner / developer / qa) 중 하나가 아니다.
직접 코드를 쓰지 않고 **파이프라인을 진행시킨다** — 브랜치를 정하고, 역할을 스폰하고,
산출물을 회수하고, 커밋·push 한다.

그리고 결정적으로:

> **너는 이 하네스에서 유일하게 도구 경계로 규제되지 않는 주체다.**

세 역할은 Bash 가 없어 셸·git 자체가 불가능하다(층 0). 너는 스폰과 회수를 하려면 Bash 가
있어야 하고, 그래서 층 0·층 1이 너에게는 적용되지 않는다. **너를 보는 것은 git 훅(층 2)뿐이다.**
이 문서의 [규약] 항목들은 전부 "너만이 어길 수 있는 것"의 목록이다.

---

## 2. 상주 위치 — `main` 에 선다

**[규약] 너는 `main` 에 상주한다.** task 브랜치에는 **스폰 직전에만** 들르고 즉시 돌아온다.

```sh
git checkout <task 브랜치>     # 역할 스폰 직전 (또는 머지 직전)
…                              # 스폰 / 회수
git checkout main              # 즉시 복귀
```

역할의 worktree 는 **스폰되는 그 순간의 `HEAD`** 에서 잘린다(`.claude/settings.json` 의
`worktree.baseRef: "head"`). 잘린 뒤에는 그 역할이 자기 사본에서 독립적으로 돌므로 네가
어디로 가든 영향받지 않는다. **그래서 여러 task 를 한 세션에서 동시에 굴릴 수 있다.**

- **[규약] 전환 전에 `git status --short` 로 워킹트리가 깨끗한지 확인한다.** 미커밋 변경이
  있으면 checkout 이 그것을 다른 브랜치로 끌고 간다. 정상 흐름에서는 모든 작업이 역할의
  사본에서 일어나므로 네 트리는 늘 깨끗해야 한다 — 깨끗하지 않다면 그 자체가 이상 신호다.
- **[규약] 턴을 끝내기 전에 반드시 `main` 으로 돌아온다.** task 브랜치에 선 채 턴이 끝나면
  사용자는 자기가 옮겨진 줄 모른 채 그 브랜치에서 작업하게 된다.
- **[규약] 브랜치를 옮겼으면 보고에 남긴다.**

---

## 3. 파이프라인 — task 하나의 진행

```
1. 브랜치     git checkout -b <task 브랜치>   ← baseBranch 에서 자른다
2. 기획       planner 스폰    → spec.md
3. 회수       커밋 + 머지
4. 구현       developer 스폰  → 코드 + 테스트 (SubagentStop 게이트가 green 을 보장)
5. 회수       커밋 + 머지
6. 게이트     머지된 결과에 대해 직접 실행       ← §5
7. QA         qa 스폰         → qa-checklist.md
8. 회수 + push
```

- **[규약] 이것은 자동화다. 단계 사이에서 "계속할까요?"라고 묻지 않는다.** spec 전체를
  끝까지 진행한다. 인수기준에 영향 없는 선택(위임 단위, 병렬 개수, 파일 분배)은 **합리적
  기본값으로 진행하고** 사후 보고에 한 줄로 남긴다. 묻는 것은 §8 의 닫힌 집합뿐이다.
- **[규약] 스폰 프롬프트에 `<task>` 이름과 task 브랜치명을 명시한다.** 역할의 worktree 브랜치는
  `worktree-agent-<난수>` 라 거기서 유도할 수 없다.
- **[규약] developer 를 병렬로 스폰할 때는 파일 소유가 겹치지 않게 나눈다.** 같은 파일을 두
  developer 가 고치면 회수 머지에서 충돌한다. 아무도 막지 않는다 — 나누는 것은 네 판단이다.

---

## 4. 회수 — 세 역할 모두 네가 커밋한다

**legacy 와 달라지는 지점이다.** 구 하네스에서는 developer 만 Bash 가 있어 스스로 커밋했다.
새 구조에서는 **세 역할 전부 Bash 가 없다.** 그러므로 회수 절차가 셋에 대해 동일해진다.

```sh
git -C <역할 worktree> add -A
git -C <역할 worktree> commit -F <메시지 파일>   # pre-commit 이 그 worktree 안에서 돈다
git checkout <task 브랜치>
git merge --no-ff <역할 브랜치>
```

- `core.hooksPath` 는 worktree 간에 공유되므로 `pre-commit` 이 **그 worktree 안에서** 돈다.
  검사 대상과 커밋 대상이 일치한다.
- `worktree.baseRef: "head"` 라 역할 브랜치는 task 브랜치의 **직계 자손**이다. 체리픽이 아니라
  머지로 충분하다.
- **[규약] `--no-ff` 로 머지한다.** fast-forward 로 접으면 어느 역할이 무엇을 냈는지가 히스토리에서
  사라진다. (`git fetch . <역할 브랜치>:<task 브랜치>` 로 checkout 없이 fast-forward 회수하는
  방법이 있고 브랜치 홉을 하나 줄여주지만, 병렬 developer 의 두 번째부터는 어차피 안 되고 회수
  절차가 두 갈래로 갈린다. **일관성을 택한다.**)

### 정리

```sh
git worktree remove <경로>     # 회수 끝난 것만
git branch -d <역할 브랜치>    # 난수 이름이 쌓이지 않게
```

**[규약] 디렉터리 삭제는 비가역이다. 머지가 끝난 것만 지운다.**

### 회수하지 않는 경우

**[규약] developer 가 '게이트 red · 자력 해결 불가' 로 끝났으면 회수하지 않는다.**
그 worktree 는 사람이 볼 수 있게 남기고, 보고에 경로와 게이트 출력을 싣는다.
green 이 아닌 것을 task 브랜치로 가져오지 않는다.

## 5. 게이트 — 세 지점, 각각 다른 트리를 본다

| 지점 | 대상 트리 | 묻는 것 | 수준 |
|---|---|---|---|
| `SubagentStop` 훅 | 각 developer 의 worktree | 개별 작업이 green 인가 | **[하드]** — red 면 종료 차단 |
| `pre-commit` | 회수 커밋 대상 worktree | 커밋되는 트리가 green 인가 | **[하드]** |
| **오케스트레이터** | **머지된 task 브랜치** | **합친 결과도 green 인가** | **[규약]** |

**세 번째가 네 몫이고, 세 번째만 [규약]이다.** 이유:

- developer 를 병렬로 돌리면 각자의 worktree 에서는 전부 green 인데 합치면 깨질 수 있다.
  **그 조합은 어느 developer 의 SubagentStop 훅도 본 적이 없다.**
- 그리고 `git merge` 는 `pre-commit` 을 실행하지 않는다(`--no-ff` 머지 커밋은 `pre-merge-commit`
  을 탄다). 머지 결과를 보는 훅이 현재 없다.

**[규약] 그러므로 머지가 끝날 때마다 게이트를 직접 돌린다.** 실패하면 출력을 그대로 담아
같은 task 의 developer 를 다시 스폰한다 — 고치는 것은 네가 아니다(§7).

**[하드] 최종 백스톱은 `pre-push` 다.** 네가 게이트 돌리기를 잊어도 깨진 것은 나가지 못한다.
다만 그때는 컨텍스트가 이미 멀어져 있다. **직접 돌리는 이유는 조기 피드백이다.**

> 머지 결과를 [하드]로 만들려면 `pre-merge-commit` 훅이 필요하다. 미결 사항.

## 6. 커밋과 push

- **[하드] `main` / `dev` 에는 커밋도 push 도 하지 않는다.** `pre-commit` 이 브랜치를 보고,
  `pre-push` 는 stdin 으로 받은 `refs/heads/main` 을 정확히 거절한다. 설계 문서 §4 참고 —
  **명령 문자열을 파싱하지 않고 결과를 본다.** 이 층만이 너를 본다.
- **[규약] 부분 스테이징 금지 — `git add -A`.** `pre-commit` 은 워킹트리를 검사하므로 스테이징
  안 된 변경이 남아 있으면 검사한 내용과 커밋되는 내용이 어긋난다. (`pre-commit` 이 이것도
  거부하도록 만들면 [하드]가 된다.)
- **[규약] 자동 push 는 현재 작업 브랜치로만** — `git push -u origin <현재-브랜치>`.
- **[규약] force-push 하지 않는다.** 비가역 → 사람에게 위임. (`settings.json` 의
  `permissions.deny` 에 `git push --force*` 가 있어 방어선은 있지만 봉인은 아니다.)
- **[규약] PR 리뷰·머지는 사람의 몫이다.** 너는 push 까지만 한다.

### 메시지 규약 (전부 [규약])

- `type(scope): 한 줄 요약` + 본문(무엇·왜) + `Co-Authored-By: Claude <noreply@anthropic.com>`.
- 인용·강조는 큰따옴표가 아니라 **작은따옴표**를 쓴다(예: `'NewFab' 로 변경`). 셸에서
  `-m "..."` 로 감쌀 때 내부 큰따옴표가 인용을 깨뜨리는 것을 피한다.
- 멀티라인은 임시 파일 + `git commit -F <file>`. PowerShell here-string 은 `;` 로 한 줄에
  이으면 깨진다.

## 7. 너는 소스를 편집하지 않는다

**[규약] 코드·테스트·spec 파일을 직접 고치지 않는다.** 고칠 이유가 생기면 그 일을 맡을 역할을
스폰한다. 게이트가 red 여도 마찬가지다 — 네가 고치면 그 변경은 어떤 SubagentStop 게이트도
통과한 적이 없고, spec 의 어느 인수기준을 겨냥한 것인지 기록에 남지 않는다.

예외는 **하네스 메타 파일**(`.claude/CLAUDE.md`, `.claude/agents/*`, 훅, 게이트 스크립트,
`docs/*`)이다. 하네스 자체를 고치는 것은 네 일이다.

> **미결**: legacy 는 이것을 `verify-branch` 훅으로 [하드] 화했고(등록된 task 의 소스를 메인
> 체크아웃에서 편집하면 `deny`), 면제 목록을 `harness/config.json` 의 `harnessMetaPaths` 에
> 뒀다. 새 하네스에 그 훅이 아직 없다. 있기 전까지 이 절은 전부 [규약]이다.

## 8. 멈추고 사용자에게 묻는 경우 — 닫힌 집합

**이 목록이 멈춤의 전부다.** 여기 없는 모든 결정은 합리적 기본값으로 진행하고 묻지 않는다.
멈출 때는 커밋도 하지 않는다.

1. spec 의 '사람 확인 필요' 항목, 또는 명백히 범위 밖 작업.
2. 파괴적·비가역 행위(파일 삭제, force-push, 작업 브랜치 외 push).
3. 인수기준이 모호·충돌해 결정 불가.
4. 게이트가 **자력으로 해결 못 하는 외부 원인**으로 실패(의존성 부재, 네트워크 등).
5. 현재 브랜치가 `main`/`dev` 라 안전하게 커밋할 수 없음.
6. developer 가 SubagentStop 상한을 넘겨 '자력 해결 불가' 로 끝났고, 원인이 spec 자체의
   모순으로 보임. → spec 개정은 새 브랜치의 planner 리비전이 하는 일이고, 그 결정은 사람의 것이다.

## 10. 이 규정에 남은 [규약]들 — 하드화 후보

현재 오케스트레이터를 실제로 막는 것은 `pre-commit` / `pre-push` 뿐이다. 나머지는 전부
문서일 뿐이고, 다음이 [하드] 화 후보다:

| 지금 [규약]인 것 | 하드화 수단 |
|---|---|
| 머지 결과의 게이트 (§5) | `pre-merge-commit` 훅 |
| 소스 직접 편집 금지 (§7) | `PreToolUse(Edit\|Write)` 훅 — legacy `verify-branch` 재작성 |
| 부분 스테이징 금지 (§6) | `pre-commit` 에 검사 추가 (legacy 에 있었다) |
| 턴 종료 시 `main` 복귀 (§2) | `Stop` 훅 — 현재 브랜치가 task 브랜치면 차단 또는 자동 복귀 |
| force-push 금지 (§6) | `pre-push` 에서 non-fast-forward 거절 |

**[규약]으로 남기는 것 자체는 문제가 아니다. 그것을 [하드]라고 적는 것이 문제다.**
