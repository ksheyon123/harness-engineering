# 하네스 설계 노트 — 역할 격리와 강제 지점

> **무엇인가**: 이 하네스가 지금의 모양인 이유. 결정과 그 근거를 남긴다.
> **무엇이 아닌가**: 계획서도 진행 상황판도 아니다. 무엇이 구현돼 있고 무엇이 아직
> 규약뿐인지는 `.claude/CLAUDE.md` 의 '현재 상태' 절이 답한다.

## 1. 파이프라인

```
planner    ──▶  spec.md (기능 목록)
developer  ──▶  테스트 코드 + 개발 코드
qa         ──▶  qa-checklist.md (spec 인수기준 ↔ 테스트 대조)
게이트     ──▶  npm test
push
```

목표는 **의도하지 않은 동작을 구조적으로 막는 것**이다. 각 단계가 "알아서 잘 하기를"
기대하지 않고, 할 수 없게 만든다.

## 2. 지켜야 할 불변식

1. **각 에이전트는 자신의 워킹트리 안에서만 파일을 다룬다.**
2. **`main` / `dev` 에는 커밋도 push 도 되지 않는다.**
3. **게이트를 통과하지 않은 결과는 회수되지 않는다.**
4. **spec 없이 코드가 쓰이지 않는다.**

## 3. 강제 지점은 층이 다르고, 각 층이 볼 수 있는 것도 다르다

불변식을 어디에 걸 것인가는 취향이 아니다. **각 층이 실제로 볼 수 있는 것**이 정한다.

| 층 | 볼 수 있는 것 | 맞는 질문 |
|---|---|---|
| agent `tools:` 화이트리스트 | 도구 유무 | **능력 자체의 제거** |
| `PreToolUse(Edit\|Write)` | 파일 경로 | **경로 소유권** |
| `PreToolUse(Bash)` | 명령 **문자열** | 취약 — fail-open |
| `permissions.deny` | 도구/패턴 접두어 | 방어선이지 봉인이 아님 |
| `SubagentStop` | 에이전트가 남긴 **결과물** | **완결성** |
| git `pre-commit` / `pre-push` | 실제 브랜치 · ref · 트리 | **브랜치 보호** |

**브랜치 보호에 맞는 층은 git 훅뿐이다.** `git commit` 은 표기가 무한하지만
(`git -C x commit`, `--amend`, alias, `&&` 체인, 변수 치환) 훅은 *결과*를 본다.
특히 `pre-push` 는 stdin 으로 `<local ref> <sha1> <remote ref> <sha1>` 를 받으므로
`refs/heads/main` 을 정확히 거절할 수 있다 — 명령을 파싱할 필요가 없다.

반대로 **git 훅으로는 "자기 worktree 만" 을 막을 수 없다.** `git -C ../다른-worktree commit`
을 하면 훅은 그 worktree 안에서 돌고 거기 브랜치는 정상이니 통과시킨다. 훅은 누가
불렀는지 모른다. 브랜치 보호와 worktree 소유권은 **다른 문제이고 같은 층에서 풀리지 않는다.**

## 4. 핵심 — Bash 는 스코프를 매길 수 없는 유일한 도구

하네스가 나눠주는 다른 도구는 전부 **인자 모양으로 판정된다.** `Edit`/`Write` 는
`file_path` 를 받으므로 `PreToolUse` 훅이 그것을 그대로 읽고 순수 함수로 결정할 수 있다.

Bash 는 **불투명한 문자열**을 받는다. 어떤 훅도 신뢰성 있게 판정할 수 없다. 그리고
결정적으로:

```sh
printf 'x' > ../worktrees/agent-9f2/src/foo.ts
```

이 한 줄에 `PreToolUse(Edit|Write)` 는 **발동하지 않는다.** 즉 어떤 역할에 Bash 를 주면
git 이 추가되는 것이 아니라, **그 역할에 대한 경로 소유권 보장 전체가 규약으로 강등된다.**

> **결론**: 문제는 git 이 아니다. 문제는 *파일을 고칠 이유가 있는 세션이 동시에 Bash 를
> 갖는 것*이다. 그러면 경로 층이 장식이 된다.

그래서 **세 작업 역할(planner · developer · qa)에는 Bash 가 없다.** Edit/Write 가 파일을
바꾸는 유일한 경로이므로, 거기 붙는 경로 소유권 판정에 우회로가 없다.

## 5. 객관 게이트는 훅이고, 주관 판단만 에이전트다

게이트를 돌리기 위해 developer 에게 Bash 를 줄 필요가 없다. **agent frontmatter 가
`hooks:` 를 지원한다** — 스코프는 그 에이전트의 수명뿐이고 끝나면 정리된다.

**훅은 에이전트의 도구 제약을 받지 않는다.** 훅은 하네스 인프라이고 에이전트는
피검사자다. 게이트를 훅으로 내리는 순간 "게이트를 돌리려면 그 역할에 Bash 를 줘야 한다"는
전제 자체가 사라진다.

객관 게이트(`npm test`)에는 **독립적으로 판단할 것이 없다.** 돌리기만 하면 되고 답은
하나다. 독립적 시각이 필요한 것은 주관 판단뿐이고 그것은 QA 가 맡는다.

> **객관 = 훅. 주관 = 에이전트.**

게이트 대상의 단일 출처는 `package.json` 의 `scripts.test` 다. 별도 설정 파일과 러너
스크립트를 두지 않는 이유는 단일 패키지에 불필요한 간접층이기 때문이고, **그 명령을
어디에도 복사하지 않는** 이유는 낡은 사본이 없는 것보다 나쁘기 때문이다 — 문서가 게이트보다
넓게 적히면 그 차이만큼 검사가 실행되지 않는데, 세션은 그것을 알아챌 방법이 없다.

## 6. 종료 훅 — 실패를 경계 밖으로 내보내지 않는다

`SubagentStop` 은 **차단할 수 있다.** 즉 단순 검증이 아니라 **강제 루프**가 된다.

```
에이전트가 끝났다고 선언
   → 훅이 검사한다
   → 실패면 종료를 거부하고 무엇이 문제인지 되돌려준다
   → 같은 에이전트가, 같은 worktree 에서, 자기 컨텍스트를 그대로 들고 이어서 고친다
```

세 역할에 하나씩 붙어 있다:

| 훅 | 역할 | 통과 조건 |
|---|---|---|
| `verify-spec.mjs` | `planner` | 이번에 쓴 `harness/<task>/spec.md` 가 있고 인계될 모양이다 |
| `verify-green.mjs` | `developer` | `npm test` 가 green |
| `verify-checklist.mjs` | `qa` | 체크리스트가 있고 **근거 없는 판정 행이 없다** |

공통 배선(`hook-kit.mjs`)이 따로 있는 이유는 셋이 같은 모양이기 때문이다 — 훅마다
복제하면 한쪽만 고쳐지고 나머지는 조용히 낡는다.

### 6.1 차단은 종료 코드가 아니라 출력으로 한다

`exit 1` 은 *non-blocking* error 라 사용자에게 메시지만 찍히고 **에이전트는 그대로 끝난다** —
훅이 도는데 아무것도 막지 못하는 상태가 된다. 차단이 성립하는 형태는 `exit 0` + stdout JSON,
또는 `exit 2` + stderr 뿐이다.

```json
{ "decision": "block", "reason": "<무엇이 문제인지>" }
```

출력은 **동기로** 쓴다. `console.log` 는 파이프에서 비동기라 곧바로 `process.exit` 하면 잘릴
수 있고, **판정이 잘려 나가면 파싱할 JSON 이 없다고 보고 종료가 허용된다.**

`reason` 은 로그가 아니라 **그 에이전트가 읽을 다음 지시문**이다. "실패했다"만 적으면 무엇을
할지 알 수 없다.

### 6.2 상한이 없으면 루프가 된다

무조건 차단하면 에이전트가 못 고치는 원인(외부 의존성, spec 자체의 모순, `<task>` 미지정)에서
영원히 갇힌다. `hook-kit.mjs` 의 `retryBudget` 이 실패 횟수를 세고, 상한을 넘으면 차단을 푼다 —
다만 **조용히 통과시키지 않고** `systemMessage` 로 "이 결과는 통과가 아니다"를 남긴다.
오케스트레이터가 회수 전에 그 신호를 본다.

카운터는 **그 트리의 gitdir**(`--absolute-git-dir`)에 둔다. 링크된 worktree 에서 그것은
`<main>/.git/worktrees/<id>` 라 **에이전트마다 자연히 격리되고 worktree 와 함께 사라진다.**
카운터가 남으면 다음 에이전트가 남의 소진분을 물려받는다.

## 7. 경계 절단 규칙 — 실패는 경계를 넘기지 않는다

`tester` 를 별도 에이전트로 두면 다음이 무너진다: developer 가 끝나고 컨텍스트가 소멸한
뒤에 tester 가 돌고, red 가 나면 수리할 주체가 없다. 새 developer 를 부르면 남이 쓴 코드를
처음 보는 상태이며, **어느 spec 의 어느 인수기준을 겨냥한 코드인지조차 모른다.**

여기서 일반 규칙이 나온다.

> **핸드오프가 완결된 산출물일 때만 경계를 자른다. 실패는 경계를 넘기지 않는다.**

| 경계 | 자를 수 있나 | 이유 |
|---|:---:|---|
| spec.md → developer | ✅ | spec 은 완결된 문서다. 앞사람의 사고 과정이 필요 없다 |
| 코드+테스트 → qa | ✅ | **자기채점 금지.** 코드를 짠 컨텍스트는 '덮었다'고 말할 이해관계가 있다 |
| red → 수리 | ❌ | 수리는 '무엇을 왜 시도했는가' 를 요구하고, 그것은 그 에이전트 컨텍스트에만 있다 |

## 8. 구조

```
오케스트레이터   Agent/Read/Grep/Glob/Bash   메인 체크아웃   git 전담 · 스폰 · 회수 · push
planner          Read/Grep/Glob/Write/Edit   worktree        Bash ❌  + verify-spec
developer        Read/Grep/Glob/Write/Edit   worktree        Bash ❌  + verify-green
qa               Read/Grep/Glob/Write/Edit   worktree        Bash ❌  + verify-checklist
```

```
층 0  agent tools              세 역할에 Bash 없음 → 셸·git 자체가 불가
층 1  PreToolUse(Edit|Write)   세션 밖 파일 편집 deny → 경로 소유권
층 2  git pre-commit/pre-push  main·dev 커밋·push 거부 — 불변식만. 게이트는 얹지 않는다(§8.1)
```

**층 1이 완전 방어가 되는 것은 층 0 아래서다.** 세 작업 역할에게 Edit/Write 가 파일을 바꾸는
유일한 경로이므로, 거기 붙인 경로 소유권 훅에 우회로가 없다. 불변식 1이 강제 가능한 문장이
되는 것은 이 조건에서다.

**층 2가 면제되지 않는 이유**: 오케스트레이터가 유일하게 규제되지 않는 주체이고, 그것은 도구
경계로 막을 수 없다(스폰과 회수를 하려면 Bash 가 있어야 한다). git 훅만이 오케스트레이터를
본다. 역할 배치를 어떻게 바꾸든 이 사실은 달라지지 않는다.

역할의 worktree 는 스폰 순간의 `HEAD` 에서 잘리므로 역할 브랜치는 task 브랜치의 **직계
자손**이다. 따라서 `git fetch . <역할 브랜치>:<task 브랜치>` 로 워킹트리 없이 fast-forward
회수가 가능하다(`--no-ff` 는 포기). developer 를 병렬로 여러 개 돌리면 두 번째부터는
fast-forward 가 아니므로 그때만 checkout + merge 가 필요하다.

### 8.1 층 2 에 게이트를 얹지 않는다

층 2 를 "git 훅" 한 덩어리로 보면 성질이 정반대인 둘이 섞인다.

| | 검사 | 비용 | 도는 곳 |
|---|---|---|---|
| **불변식** | 브랜치가 `main`/`dev` 아닌가 · 전체 스테이징인가 | ms | `pre-commit` · `pre-push` |
| **게이트** | `npm test` 가 green 인가 | 분 | git 훅이 **아닌** 곳 |

게이트를 `pre-commit` 에 얹으면 안 되는 이유가 셋이다.

**(1) 중복이다.** 회수 시퀀스에서 `pre-commit` 이 보는 트리는 이것이다:

```sh
git -C <역할 worktree> add -A
git -C <역할 worktree> commit -F <메시지 파일>     # ← pre-commit
```

방금 `SubagentStop` 훅이 green 을 확인하고 통과시킨 바로 그 트리다. 훅과 커밋 사이에
그것을 건드린 주체가 없다. planner·qa 의 회수는 더하다 — 문서만 만든다.

**(2) 첫 실행은 공짜였지만 두 번째는 아니다.** 세 역할 모두 `background: true` 라
`SubagentStop` 게이트는 크리티컬 패스 밖에서 지불된다. `pre-commit` 의 재실행은
**오케스트레이터의 포그라운드**에서 돈다 — 사용자와의 대화를 세워두고. 회수는 백그라운드
역할이 끝날 때마다 대화 중간으로 끼어드는 일이고, 그 인터럽트가 ms 냐 분이냐가 여기서
갈린다. 턴 경합 자체는 세션이 하나인 이상 없앨 수 없다. **없앨 수 있는 것은 그 턴의
길이다.**

**(3) 정작 봐야 할 트리를 `pre-commit` 은 보지 못한다** — §8.2.

### 8.2 게이트가 도는 지점

**`pre-commit` 이 "머지된 task 브랜치" 를 본다는 것은 성립하지 않는다.** 자연스러운 오해라
따로 적어둔다.

- 머지 커밋에는 `pre-commit` 이 아니라 **`pre-merge-commit`** 이 돈다(git 2.24+).
  `pre-commit` 으로 되돌아오는 것은 충돌을 손으로 풀고 따로 커밋할 때뿐이다.
- §8 이 권하는 fast-forward 회수는 더하다:

  ```sh
  git fetch . <역할 브랜치>:<task 브랜치>     # 커밋이 생기지 않는다 → 훅이 하나도 돌지 않는다
  ```

즉 `pre-commit` 에 게이트를 얹으면 **필요 없는 곳에서는 돌고 필요한 곳에서는 안 돈다.**
비용은 최대, 보장은 0 인 조합이다.

게이트는 **새 트리가 처음 생기는 지점에서만, 그리고 포그라운드 밖에서** 돈다:

| 지점 | 대상 트리 | 묻는 것 | 비용을 지불하는 곳 |
|---|---|---|---|
| `SubagentStop` 훅 | 각 developer 의 worktree | 개별 작업이 green 인가 | 그 서브에이전트 수명 안 (`background`) |
| 오케스트레이터, 머지 직후 | 머지된 task 브랜치 | 합친 결과도 green 인가 | `run_in_background` — 턴이 즉시 끝난다 |

둘은 중복이 아니다. developer 를 병렬로 돌리면 각자의 worktree 에서는 전부 green 인데
합치면 깨질 수 있고, **그 조합은 어느 developer 의 훅도 본 적이 없다.**

### 8.3 push 만은 강제가 필요하다 — verified marker

두 번째 지점은 오케스트레이터가 돌리는 **규약**이라 강제력이 없다. 마지막 비가역 지점인
push 는 훅으로 막아야 하는데, `pre-push` 에서 게이트를 통째로 돌리면 §8.1(2)가 되돌아온다.
검사와 실행을 분리한다:

- 게이트가 green 으로 끝나면 그 트리의 sha 를 기록한다.
- `pre-push` 는 stdin 의 `<local ref> <sha1> <remote ref> <sha1>` 만 읽고 둘을 본다 —
  **(a)** `refs/heads/main`·`dev` 인가(거절), **(b)** 밀려는 sha 가 기록에 있는가.
  없으면 **그때** 게이트를 돈다.

정상 경로는 ms 이고, 우회 경로는 느릴 뿐 열려 있지 않다.

> **기록 위치는 `git rev-parse --git-common-dir` 이다 — `--absolute-git-dir` 이 아니다.**
> 링크된 worktree 에서 후자는 `<main>/.git/worktrees/<id>` 를 주므로 그 worktree 와 함께
> 사라지고 다른 트리에서 보이지 않는다. marker 는 적는 쪽(게이트를 돌린 트리)과 읽는 쪽
> (push 하는 트리)이 다를 수 있으므로 공유돼야 한다.
>
> `hook-kit.mjs` 의 재시도 카운터는 **의도적으로 반대**를 쓴다(§6.2) — 에이전트별로
> 격리되고 worktree 와 함께 사라지는 것이 거기서는 맞는 성질이다. 두 용도가 요구하는
> 스코프가 반대라는 것을 배선할 때 혼동하지 않아야 한다.

### 8.4 회수 시퀀스는 스크립트, 강제는 훅

회수는 세 역할에서 모두 같은 고정 시퀀스다 — worktree 경로·브랜치명·메시지가 정해지면
답이 하나다. §5 의 선("객관 = 훅, 주관 = 에이전트")이 그대로 적용되므로 오케스트레이터가
매번 즉흥으로 조립하지 않고 결정적 모듈로 고정한다.

`.claude/hooks/` 의 훅들이 이미 테스트를 갖고 있는 것과 같은 이유다 — **그 모듈은 게이트가
검사할 수 있다.** "역할 브랜치가 task 브랜치의 자손이 아니면 거절" 같은 판정을 테스트로
못박을 수 있다는 것이, 매 회수마다 다시 해석되는 프롬프트 대비 결정적 차이다.

> **단, 불변식을 그 스크립트에 넣지 않는다.** 스크립트를 쓰라고 강제하는 것이 없어서
> `git commit` 을 직접 치면 그대로 우회된다. 스크립트는 편의, 훅은 강제다 — 스크립트가
> 없어도 하네스는 안전해야 하고, 훅이 없으면 안전하지 않다.

## 9. QA — 게이트의 사각지대

게이트는 **"테스트가 통과했나"** 를 안다. QA 는 **"그 테스트가 spec 을 덮는가"** 를 답한다.

해피패스만 검증하는 얕은 테스트도 green 이고, **게이트는 그것을 구조적으로 볼 수 없다.**
그 사각지대가 QA 의 자리다. 대조는 기능이 아니라 **인수기준 단위**로 한다 — 기능 단위면
"관련 테스트가 하나 있으니 통과"가 되어 부분 커버리지가 통째로 숨는다.

QA 는 **비차단**이다. 최종 확인자는 사람이고, QA 는 사람이 코드를 열어보지 않고도 결정할 수
있는 표를 남긴다.

### 9.1 증거 규칙 — 위험의 방향이 뒤집혀 있다

**초록 행은 사람이 다시 보지 않는다.** 그래서 이 표에서 가장 위험한 출력은 잘못된 통과다.
누락을 잘못 적으면 사람이 확인하고 넘어가지만(소음), 통과를 잘못 적으면 **아무도 확인하지
않는다**(침묵).

그래서 판정마다 인용을 요구한다 — 통과에는 `파일 > 테스트 이름`, 부분에는 무엇이 안 덮였는지,
`❌ (구현 있음)` 에는 구현 위치. **인용하지 못하면 한 단계 내려간다.** 과소평가는 사람이
바로잡지만 과대평가는 그대로 통과한다.

구현 여부는 `❌` 행에서만 따진다. 통과·부분인 행은 그 테스트가 돌고 있으므로 구현이 있는
것이 자명하다.

인용이 *맞는지*는 훅이 판정할 수 없다. 하지만 **있는지**는 확실히 알 수 있고, 그것이
`verify-checklist` 가 하는 일이다. 그 훅이 없으면 이 규칙은 부탁일 뿐이다.

## 10. 검토했으나 배제한 것

### committer 에이전트 (커밋·push 전담 역할)

**결론은 두지 않는 것이다. 다만 흔히 드는 배제 근거 중 둘은 사실이 아니다** — 틀린 근거를
남겨두면 나중에 그 구멍을 발견한 사람이 결론까지 함께 뒤집는다.

#### 사실이 아닌 배제 근거

- **"격리를 가질 수 없다"** — 성립하지 않는다. worktree 는 **object DB 와 ref 네임스페이스를
  공유한다.** 갇히는 것은 워킹트리뿐이고 git 그래프는 하나다. 격리된 committer 도
  `git -C <다른 worktree> add -A && commit` 으로 공유 ref 를 움직일 수 있고,
  `git fetch . <역할 브랜치>:<task 브랜치>` 로 워킹트리 없이 회수할 수 있으며,
  오케스트레이터가 `main` 에 상주하므로 자기 사본에서 `git checkout <task 브랜치>` 후
  머지·push 까지 할 수 있다.
- **"오케스트레이터와 HEAD 를 놓고 다툰다"** — 위 전제 위에 서 있던 논거다. 격리를 주면
  HEAD 가 따로라 경합이 없다.

**committer 는 기술적으로 완전히 성립한다.** 배제는 불가능해서가 아니라 값이 없어서다.

#### 실제 배제 근거

- **§5 에 걸린다 — 객관 = 훅.** 커밋·머지·push 에는 독립적으로 판단할 것이 없다. 고정
  시퀀스를 위해 에이전트를 두는 것은 tester 를 두는 것과 같은 종류의 실수이고, 맞는 형태는
  §8.4 의 스크립트다.
- **§7 에 걸린다 — 머지 충돌.** developer 를 병렬로 돌리면 충돌은 예외가 아니라 정상 발생
  경로다. 해소는 *양쪽이 각각 무엇을 의도했는가* 를 요구하고, 그 지식은 spec 을 읽고 스폰
  프롬프트를 짜고 보고를 받은 오케스트레이터의 컨텍스트에만 있다. 머지된 트리 게이트의
  red 도 마찬가지다. **실패는 경계를 넘기지 않는다.**
- **강제력을 더하지 않는다.** committer 도 프롬프트로 "main 에 커밋하지 마라" 를 받을 뿐이고,
  그것은 CLAUDE.md 문장과 정확히 같은 층이다. 층 2를 면제해주지 않고, 층 2가 서면 committer 가
  주려던 안전은 committer 없이 전부 얻어진다.
- **"git 을 만질 수 있는 세션이 정확히 하나" 는 이미 참이다.** committer 는 그 하나를
  *옮기는* 것이고, 오케스트레이터가 Bash 를 유지하면(머지된 트리 게이트·worktree 정리 때문에
  유지해야 한다) **둘로 늘린다.**

#### 검토한 변형 — "세션 시작에 committer 가 상주한다"

per-commit 스폰의 두 약점(스폰·보고 왕복, 매번 fresh context)을 실제로 무력화하는 제안이라
따로 본다. 배선이 셋이고 셋 다 결론이 다르다.

**(a) 서브에이전트를 한 번 띄우고 `SendMessage` 로 부린다.** 하네스 안에서 상주에 가장 가까운
배선이지만 **인터럽트를 줄이는 게 아니라 늘린다.** 서브에이전트는 대기하지 않는다 — 한 턴
돌고 끝나고, 깨워야 다시 돈다. 그리고 깨우는 주체가 오케스트레이터다:

```
developer 종료  → 오케스트레이터 깨어남 (턴 1) → SendMessage(committer)
committer 종료  → 오케스트레이터 깨어남 (턴 2) → 결과 확인 · 다음 진행
```

서브에이전트 완료 통지는 부모 세션으로만 간다. committer 는 developer 의 종료를 직접 알 수
없다. 오케스트레이터가 인라인으로 git 을 부르면 턴 1회인 것이 2회가 된다.

**(b) `SessionStart` 훅으로 별도 프로세스를 띄운다(데몬).** 이것만이 턴 경합을 실제로 푼다.
대가:

- 깨어날 신호가 없다 — `git worktree list`/파일시스템 **폴링**이 된다.
- 두 프로세스가 같은 저장소를 동시에 쓴다 — `index.lock` 경합, `git worktree remove` 와의
  레이스. 이론적 위험이 아니라 일상 경로다.
- 규제되지 않는 Bash 세션이 **둘**이 된다. 오케스트레이터의 Bash 는 뺄 수 없다.
- 사용자 시야 밖에서 브랜치를 옮기고 push 한다. 오케스트레이터의 git 조작은 최소한
  트랜스크립트에 남는다.
- 명시적 **멀티 세션 설계**다. "세션 하나로 충분하다" 를 되돌린다면 근거가 데몬의 편의보다
  커야 한다.

**(c) 그것은 에이전트가 아니라 스크립트다.** "항상 떠 있다" 가 사려던 성질 — *언제나 같은
방식으로, 즉흥 없이, 즉시* — 는 상주가 아니라 **결정성**에서 나온다. 스크립트는 뜰 필요 없이
항상 거기 있고, 상주 에이전트에는 없는 것을 준다: **테스트 가능성**(§8.4).

> committer 가 정당화되려면 회수가 **원래** 비싸야 한다. 그 비쌈은 `pre-commit` 에 게이트를
> 얹은 데서 왔다(§8.1). **비용을 고칠 일이지 소유권을 옮길 일이 아니다.**

### tester 에이전트

§7 참고. 실패가 경계를 넘어가 컨텍스트를 잃는다.

### PreToolUse(Bash) 로 명령을 파싱해 경계를 검증하는 방식

셸 한 줄의 표현 공간이 너무 넓어(변수 치환, 서브셸, 심볼릭 링크, `pushd`) fail-open 이다.
경로 하나를 판정하는 데도 수백 줄이 들고, 그러고도 새는 구멍을 셀 수 없다. §4 의 결론대로
**Bash 를 주지 않는 것**이 유일하게 견고한 답이다.

### QA 의 spec 자체 감사

QA 가 spec 을 독립적으로 재도출하면 기획의 누락도 드러난다. 그러나 QA 는 파이프라인의
끝이라 그 발견 시점이 **이미 구현 후**다. 고치려면 새 브랜치 + spec 리비전 + 재구현이고,
이것은 §7 의 "실패는 경계를 넘기지 않는다"를 어긴다. spec 의 완성도는 사람이 판단하고,
QA 는 대조 하나에 집중한다.

### 게이트 대상을 위한 별도 설정 파일

`package.json` 의 `scripts.test` 가 이미 표준 단일 출처다. 자체 포맷을 만들면 원본이 둘이
되고, 그중 하나는 이 저장소에서만 통한다. §5 참고.
