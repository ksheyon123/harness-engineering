# 기획자 모드

**작업 세션의 첫 모드다.** 논의를 어디서 하는가 · 격리에 언제 들어가는가 · spec 을 어떻게 쓰는가가 전부 여기 있다.

자리·모드 전환·검증·커밋/push·worktree 규약은 `.claude/harness.md` 에 있다. 그쪽이 **모든 세션과 모든 서브에이전트**에 실리므로, 작업 세션 하나만 쓰는 이 절차는 여기 둔다 — 읽는 것은 spec 을 쓰기 직전 한 번이다.

에이전트 정의가 아니다. **스폰할 것이 없다** — 기획자는 서브에이전트가 아니라 세션의 첫 모드다.

## 논의 — 저장소 본체에서

**논의는 저장소 본체에서 한다.** 그 구간은 순수 읽기라 안전하고, 브랜치 이름은 논의의 결과라 미리 worktree 로 들어갈 수도 없다.

**논의 방식은 `.claude/planner/` 의 `*.md` 가 실어 준다** — 세션이 열리는 순간 이미 주입돼 있다. 하네스는 `grilling.md`(결정 트리를 라운드로 훑는 법)를 기본으로 깔아 주고, 설치한 프로젝트는 그 디렉터리를 갈아끼워 자기 방식을 쓴다.

**사실을 찾는 것은 네 몫이다.** 파일·심볼·기존 구현처럼 열어보면 확인되는 것은 사람에게 묻지 말고 직접 찾거나 탐색 에이전트에게 시킨다. 사람에게 물을 것은 **결정**이다. (`developer`·`qa` 스폰은 이 모드에서 하지 않는다 — 그건 spec 커밋 뒤 오케스트레이터 모드의 일이다.)

## 격리 진입

task 가 정해지면 격리로 들어간다:

```
EnterWorktree(name: <task>)
git branch --show-current      # 실제 브랜치명을 확인한다
```

`EnterWorktree` 가 브랜치를 만드는데 **준 이름 그대로가 아니다**(`feat/x` → `worktree-feat+x`). 그 이름이 그대로 PR 이름이 되므로, 원하는 이름이 따로 있으면 **여기서** `git branch -m <원하는 이름>` 으로 고친다 — push 후에 고치려면 원격 브랜치 삭제까지 얽힌다. 그리고 `git branch --show-current` 로 **확인한 값**을 아래 frontmatter 에 적는다. 추측하면 없는 브랜치를 가리키게 된다.

## 산출물

`harness/<task>/spec.md` 한 파일.

**세션은 끝나면 닫힌다. spec 에 안 적힌 것은 없는 것이다.** 다음 세션도, `developer` 도, `qa` 도, PR 을 보는 사람도 이 파일만 본다. 그 사실이 곧 완결성의 압력이다.

## 신규 작성 / 리비전 판별

`harness/<task>/spec.md` 를 먼저 Read 해 본다.

- **없으면** — 신규 작성. 아래 형식대로 처음부터 쓴다.
- **있으면** — **리비전 모드.** 파일을 처음부터 다시 쓰지 않는다:
  - 요청된 변경에 해당하는 기능 항목만 추가·수정하고, **바뀌지 않은 기능은 그대로 보존한다.**
  - frontmatter 의 `branch:` 값**만** 현재 브랜치로 갱신한다.
  - 파일 맨 아래 `## 개정 이력` 절(없으면 새로 만든다)에 한 줄 추가: `- <YYYY-MM-DD> <이전 브랜치> → <현재 브랜치>: <무엇을 왜 바꿨는지>`.
  - `## 개정 이력` 은 리비전 때만 생긴다 — 신규 작성 spec 에는 넣지 않는다.

> **한 브랜치는 spec 을 정확히 한 번만 확정한다.** 개정이 필요하면 원본에서 새 task 브랜치를 자르고 그 위에서 다시 기획자 모드로 시작한다. **`pre-commit` 이 강제한다** — 브랜치가 base 이후로 spec 을 둘 이상 *추가*하면 거부된다. 기존 spec 을 고치는 리비전은 추가가 아니라 통과한다.

## spec.md 형식

**frontmatter 가 필수다.** 첫 줄이 `---`, 그 안에 `branch: <브랜치>`, 그리고 닫는 `---`. `branch:` 에는 [격리 진입](#격리-진입)에서 확인한 실제 값을 적는다.

```markdown
---
branch: <현재 브랜치>
---

# <태스크명>

## 목적
이 작업이 무엇인지 1~3문장.

## 배경
왜 지금 이걸 하는가.

## 기능 목록

### 기능: <기능명>
- **의도**: 이 기능이 왜 필요한가 (목적)
- **방식**: 어떻게 구현해야 하는가 (접근/제약)
- **주의**: 놓치기 쉬운 엣지 케이스·함정
- **인수기준**: 무엇이 참이면 이 기능이 완성인가 (검증 가능한 단언)

### 기능: <다음 기능>
- ...

## 버린 대안
검토했으나 택하지 않은 접근과 **그 이유**.

## 범위 밖
이 task 에서 만들지 않는 것.
```

### `배경`·`버린 대안`·`범위 밖` 이 필수인 이유

| 절 | 없으면 무슨 일이 생기나 |
|---|---|
| `## 배경` | 나중에 이 spec 을 읽는 사람이 왜 이런 결정이 내려졌는지 복원할 수 없다 |
| `## 버린 대안` | **스폰 프롬프트로는 절대 안 넘어가는 정보다.** `developer` 가 기각된 접근을 다시 택하고, 새 세션이 같은 논의를 반복한다 |
| `## 범위 밖` | `developer` 는 자율 진행하도록 되어 있어 **선의로 범위를 넓히기 쉽다.** 그걸 막는 유일한 문장이 여기다 |

인수기준이 **무엇을 만들지**를 정한다면, 뒤의 둘은 **무엇을 만들지 않을지**를 정한다.

**버린 대안에는 이유를 적어라.** "monotone chain 을 안 쓴다"만 적으면 `developer` 가 "더 짧은데요" 하고 갈아탄다. "더 짧은 것은 사실이나, 분할정복 재귀 구조 자체가 이 작업의 관심사라 택하지 않았다"까지 적어야 근거가 된다.

## 인수기준 작성 지침

각 기능의 **인수기준**은 나중에 테스트로 옮길 수 있도록 **검증 가능한 단언**으로 쓴다.

- 좋음: "동일 code 로 2회 진입해도 교환 POST 는 1회만 발생한다"
- 나쁨: "로그인이 잘 동작한다" (검증 불가)

구체적인 입력과 기대값을 적으면 `qa` 가 테스트와 대조할 때 주관이 개입할 여지가 줄어든다. `[(0,0),(1,1),(2,2)] → [(0,0),(2,2)]` 처럼 값으로 쓸 수 있으면 값으로 쓴다.

## task 경계

| 물음 | 같은 task 로 묶을 이유 |
|---|---|
| **파일이 겹치나** | 겹치면 묶는다 — 안 묶으면 최종 머지에서 충돌한다 |
| **순서 의존이 있나** | A 없이 B 가 성립 안 되면 묶는다. task 는 병렬로 굴러간다 |
| **따로 리뷰·머지돼도 되나** | 되면 나눈다. task = 브랜치 = PR 하나다 |

"개념적으로 다른 기능인가"는 기준이 아니다. 로그인과 로그아웃은 개념상 다르지만 같은 파일을 건드리니 한 task 고, `## 기능 목록` 에 항목 둘로 들어간다.

## 규칙 — 도구 경계

- **`harness/` 아래에만 쓴다.** 코드와 설정은 이 모드에서 수정하지 않는다 — **층 1 이 강제한다**(`path-ownership.mjs`). **경로 목록을 여기 적지 않는다**: 그것은 `harness.config.json` 이 프로젝트마다 정하는 값이라, 베껴 적으면 설치된 프로젝트에서 틀린 값이 된다. 읽기는 자유롭게 — 현재 코드를 파악해 근거 있게 써라.
- **코드를 작성하지 않는다.** "무엇을 · 왜 · 어떻게"를 명세할 뿐이고, 구현은 `developer` 가 한다.
- **체크박스(`[ ]`/`[x]`)를 만들지 않는다.** 기능을 *열거*한다. 완료 판정은 `qa` 와 사람의 몫이다.
- 파괴적·비가역 행위가 필요하면 직접 하지 말고 spec 에 **"사람 확인 필요"** 로 적는다.

## 마무리 — 끝은 셋이고 순서가 있다

| 무엇의 끝 | 판정 | 어디가 정하나 |
|---|---|---|
| **논의** | 물을 것이 남지 않았다 | `.claude/planner/` 의 논의 지침 |
| **문서** | **이 파일만 읽고 구현할 수 있는가?** | 이 문서 |
| **모드** | spec 커밋 = 사람의 승인 | `harness.md` |

**경쟁하는 판정이 아니라 직렬이다.** 논의가 끝나야 문서를 닫을 수 있고, 문서를 닫아야 커밋한다. 커밋하는 순간 오케스트레이터 모드이고, **그 뒤로는 아무도 이 spec 을 고치지 않는다 — 네가 저자여도 마찬가지다.**
