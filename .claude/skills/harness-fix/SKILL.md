# 하네스 수정 — 실행자가 직접 받는다

**이 요청은 넘기지 않는다.** `/task` 도, `harness spawn` 도 부르지 않는다.

## 왜 넘기면 안 되나

넘어간 곳에 **구현할 자리가 없다.** 층 1(`path-ownership.mjs`)이 작업 세션과 `developer` 양쪽에서 하네스 파일을 `deny` 한다 — 넘기면 논의를 다 하고 spec 까지 커밋한 뒤, `developer` 의 첫 편집에서 막힌다.

파이프라인을 태울 수 없는 더 근본적인 이유도 있다: **훅을 고치러 `developer` 를 스폰하면 그 훅이 그 developer 의 종료를 검사한다.** 순환이다.

## 절차

실행자는 저장소 본체에 서 있어 **worktree 격리가 없다.** 그래서 브랜치만이 안전장치다.

1. **브랜치를 자른다.** `main`/`dev` 에 직접 커밋하지 않는다. `pre-commit` 이 막지만 그건 층 2 라 `--no-verify` 로 열리는 방어선이다 — 기대지 마라
2. 고친다
3. **`git add -A`** — 부분 스테이징은 `pre-commit` 이 거부한다. 검사한 것과 커밋되는 것이 달라서는 안 된다
4. 커밋한다
5. **커밋한 뒤에 `harness gate` 를 돌린다.** 순서가 중요하다 — `pre-push` 는 **올리려는 sha** 의 게이트 기록을 본다. 커밋 전에 돌린 green 은 그 커밋의 것이 아니라서 push 가 거부된다. 그리고 **손으로 `npm test` 를 치면 기록이 안 남는다** — 검사는 되지만 push 에서 막힌다
6. **작업 브랜치로만 push** 한다(`git push -u origin <현재-브랜치>`). `main`/`dev` 엔 절대 안 한다. force-push 도 안 한다 — 비가역이라 사람에게 위임한다

PR 리뷰·머지는 사람의 몫이다.

## 여기 해당하지 않는 것

`src/**` 와 `harness/**`(spec·체크리스트)는 **층 1 이 실행자에게 `deny`** 한다. 작업하다 그쪽이 나오면 하네스 수정이 아니라 제품 작업이다 — 거기서 멈추고 `/task` 로 넘긴다.

문서(`README` · `docs/**`)는 층이 가르지 않는다. **규약이 정한다: 실행자 자리다.**
